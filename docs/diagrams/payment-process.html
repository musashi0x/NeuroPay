neuro-pay — Payment Process

How an autonomous agent pays a paid API per call, with no API key, no card, and one HTTP status code doing the whole handshake.

Diagram reflects the current x402 flow in apps/api/src/routes/streams/next.ts & the seller pipeline; see README §“The use case” for the canonical walkthrough.

Buyer agent + grant
OWNER One-time human approval, then the agent runs unattended.
1Grant is approved
A human signs a policy once: spend cap, expiry, explicit allowlist of calls. The policy lives on chain — the cap and expiry are enforced by Permit2, not by trust.
3Request without credentials
The agent calls GET /v1/streams/:id/next with no API key, no card, no auth header — just the URL.
5Server-side sign & retry
Browser never sees a key. The session key signs an EIP-712 Permit2 witness bound to the recipient, amount, nonce, and expiry. The agent retries with X-PAYMENT attached.
Gateway Hono API · apps/api
CORE All of the verification and metering happens here. HTTP is the boundary.
2Advertise demand
Every call to a paid endpoint is shaped by the metering policy — pinned price per unit, accrual threshold, tick interval. The gateway knows what the next unit of work will cost before it is asked.
4Reply 402 Payment Required
Body carries amount, token (npUSD), chainId (97), recipient (payTo), and spender (the settler EOA — the wire also pins the msg.sender Permit2 will see).
6Verify & check idempotency
ERC-1271 against the session's smart account. The EIP-712 digest is recomputed server-side, so a wrong-chain payment fails the signature check, not a field compare. A replayed nonce returns the cached segment — no new charge.
7Expose → deliver → enqueue
Exposure ceiling reserves SETTLEMENT_THRESHOLD × MAX_IN_FLIGHT_SETTLEMENTS of seller credit. On pass, the segment is produced and the response returns immediately. Settlement is not awaited — it's enqueued.
BNB Chain 97 · Permit2 · npUSD
LEDGER OF TRUTH Three addresses, not two.
8Submit on chain
The settler EOA calls Permit2.permitWitnessTransferFrom. Permit2 checks the signed spender against msg.sender, the witness recipient, and the cap/expiry on the grant — all enforced by the contract, not the gateway.
9Confirm or fail
A confirmed settlement calls recordSettle (capped at accruedUnpaid), releasing the exposure slot and crediting the meter. A failed settlement keeps the slot reserved until operator retry or restart.
Seller service the API being paid
PAID Credit exposure is bounded; work only happens after the meter says it can.
10Produce the next segment
The endpoint runs only after verify + exposure pass. The response carries the segment plus accruedUnpaid and totalAccrued (bigints) so the console can render the budget in real time.
11Append to the ledger
Every stage — payment.verified, segment.delivered, settlement.submitted, settlement.confirmed — is written to the append-only SQLite ledger (packages/ledger). The console reads from there.
12Push live update
Each ledger append fires hub.notify() and the change streams out to the web console over GET /v1/events (SSE) — what the operator sees, not what the buyer does.

What is bounded

  • Spend cap — enforced by the Permit2 contract on chain.
  • Expiry — enforced on chain, not by trusting the gateway.
  • Seller credit exposure — bounded to SETTLEMENT_THRESHOLD × MAX_IN_FLIGHT_SETTLEMENTS.
  • Nonce replay — same nonce returns the cached segment, no double charge.

What is not bounded (honest limits)

  • Signatures are stubbed in the dev runtime — production uses ERC-1271 via Permit2.
  • Settlement is in-memory unless SETTLER_PRIVATE_KEY + RPC_URL are set.
  • On-chain revoke is wired only when ADMIN_PRIVATE_KEY + RPC_URL are set.
  • Without a real spender, the signatures pnpm demo produces are not settleable on chain.
